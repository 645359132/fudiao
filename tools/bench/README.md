# 性能基准（M1-12）

需求第八章“大作品操作”：基础集（10 万汉字、40 章）与连载规模集（200 万汉字、800 章）上，章节切换不超过 1 秒，连载规模集的全文查找不超过 2 秒；“保存反馈”：停止输入后 2 秒内显示已保存（减去 800 毫秒防抖，保存本身不超过 1.2 秒）。

- `corpus.ts`：测试集生成器。固定种子，任何平台生成相同内容；文字由短句随机组合，约三成对话，偶有长段落。
- `benchmarks.ts`：在 Node 端（better-sqlite3，与桌面端共用迁移与仓储代码）测数据操作。每项给出中位数、P95 与最大值，有目标的按最大值判定。
- 界面渲染（TipTap 载入一章、结果列表）与 Tauri 命令的往返不在此列，在真实窗口中按 `apps/desktop/MANUAL_TESTS.md` 的 M1-12 一节记录。

运行（有未达标项时退出码为 1）：

```bash
pnpm bench basic
```

```bash
pnpm bench serial --json bench-serial.json
```

把测试集写成 TXT，供在应用中“导入 TXT”：

```bash
pnpm bench serial --txt serial.txt
```

### 2026-10-25，开发机：计划页（M5-07 补充）

作者反馈：200 章的书点左侧的“计划”要卡很久。在作者那部书的副本上（200 章、195 份长篇记忆、200 份章节计划、1,814 条审核问题）用临时脚本测量（Node 与 jsdom，同一台开发机），不在 `pnpm bench` 中：

| 项目 | 优化前 | 优化后 |
| --- | --- | --- |
| 读计划视图（`planningView`，进程内） | 40 至 70 毫秒 | 不变 |
| 点“计划”到页面出来（读数据加渲染） | 约 1,600 毫秒 | 约 150 毫秒 |
| 页面上的元素 / 输入框 | 41,796 / 12,604 | 573 / 4（含左栏与目录） |

慢在渲染：每章一份计划表单（人物与伏笔的勾选框、文本框）与长篇记忆的内容，收起时也全部建出来。现在展开时才建；章数多于 60 时，成书进度的表格与章节计划各自在一个滚动框里，只渲染看得见的几十章。浏览器预览里 205 章的演示作品点“计划”约 150 毫秒出现。

同一天重跑连载规模集，数据层各项仍全部达标。分卷之后查找按书中顺序排序（视图 `chapter_book_order`），扫描查找比上表慢一些（“灯”约 37 毫秒、“鲸鱼”约 30 毫秒），仍远低于 2 秒的目标；试过分批扫描，命中多时更快、没有命中时更慢，没有采用。
