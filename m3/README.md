# M3 评估：写手与审核

M3 评估回答两个问题（施工文档 M3-09）：

1. 写手与审核能不能把一部短篇连续走完“章节计划 → 写手成章 → 长篇记忆 → 审核”，写出来的东西作者愿不愿意接着改。
2. 审核能不能指出人为植入的问题：与锁定设定冲突、视角越界、伏笔提前说破。检出率记在这里。

| 路径 | 内容 | 是否入库 |
| --- | --- | --- |
| `eval/book.json` | 短篇的材料：大纲、设定（含锁定）、伏笔，以及要植入的 6 处问题 | 是 |
| `eval/config.example.json` | 模型服务配置的示例 | 是 |
| `eval/config.json` | 你自己的模型服务配置 | 否 |
| `runs/` | 每次评估的作品库、报告与全书正文（含真实的模型调用记录） | 否 |
| `RESULTS.md` | 各次评估的结果与结论 | 是 |

评估脚本在 `tools/m3-eval/`，只调用应用服务层的用例（与桌面应用走的是同一套代码），不经过界面。

## 步骤

1. 把 `eval/config.example.json` 复制为 `eval/config.json`，核对模型名、能力与价格（美元 / 百万 Token）。示例取自 `m0/experiments/deepseek.yaml`（M0 实验用的 DeepSeek 配置，价格为当时的高峰价），换别的服务时按服务商文档填写。API Key 不写进文件，只写环境变量的名字。
2. 在自己的终端里设置环境变量（PowerShell）：

   ```powershell
   $env:DEEPSEEK_API_KEY = "……"
   ```

3. 先试跑两章，确认配置可用：

   ```bash
   pnpm m3:eval --config m3/eval/config.json --chapters 2
   ```

   命令会先显示预计的调用次数、Token 与费用（偏高的估计），确认后才开始。

4. 跑完整的 6 章：

   ```bash
   pnpm m3:eval --config m3/eval/config.json
   ```

5. 读 `runs/<时间>/report.md` 与 `book.txt`，把结果记入 `RESULTS.md`。

## 评估做了什么

1. 新建作品，写入大纲、设定（林舟、钱四、玉佩为锁定设定）与两条伏笔。
2. 由大纲生成 6 章的计划草稿并采用。
3. 逐章：写手成章 → 生成长篇记忆 → 审核（程序检查加模型审核）。
4. 导出这时的全书正文（`book.txt`）。
5. 把 6 处有问题的文字分别插进对应章节的中间，重新审核这些章节。审核在植入的那一段上提出了问题记为“检出”；问题的类型在预期之内记为“类型也对”。

## 怎么读报告

- **流程**：是否全部走完；中途停下时写明停在哪一步。
- **各章**：字数与计划字数、写作与审核的耗时、审核提出的问题数。
- **植入问题的检出**：总检出率与分种类的检出率，每一处的结果与审核的说法。
- **植入之前审核提出的问题**：出在写手自己写的正文上，需要你对照正文判断哪些是真问题、哪些是误报。
- **用量与费用**：来自作品库的调用记录。

需要你本人判断并记入 `RESULTS.md` 的事：

1. 通读 `book.txt`：情节是否按计划推进，前后是否接得上，伏笔是否埋下并回收，你愿不愿意在它上面接着改。
2. 植入之前的问题里，真问题与误报各有几条。
3. 没有检出的植入问题，是提示词的缺口，还是材料不够。

## 说明

- 植入的文字是固定的，章节正文每次由模型写出，所以同一处植入在不同的运行中上下文不同，检出与否会有波动；结论以多次运行为准。
- 伏笔的两处植入换了说法（没有照抄揭晓内容），程序的字面检查查不出来，检出与否看模型审核。
- 评估用的是确定的短篇材料，不代表长篇连载的规模；长篇记忆在 6 章的规模下压力不大。
